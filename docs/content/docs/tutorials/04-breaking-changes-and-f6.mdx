# 4. Breaking Changes and Scenario F6

Scenario F6 of the specification follows one namespace from September to November 2026. It is the reference behaviour for migrations and it is replayed by `make demo`, by `TestE2E_F6` and by the fourth Jupyter notebook.

```bash
make demo
```

---

## The Two Versions

| Version | Class | Admitted policy actions |
|:---|:---|:---|
| `1.0.0` | `initial` | `odrl:use`, `ex:access` |
| `2.0.0` | `breaking` | `odrl:use`, `odrl:read` |

Three messages are sent again and again: **m1** uses `odrl:use` (valid in both), **m2** uses `ex:access` (valid only in `1.0.0`), **m3** uses `odrl:read` (valid only in `2.0.0`).

---

## Dates

`1.0.0` is approved on 2026-09-01 at 10:00. With a propagation window of two days it takes effect on 09-03.

`2.0.0` is approved on 2026-10-01 at 10:00:

- An attempt with `grace_window: P3D` is refused with `DATES_GRACE_TOO_SHORT`: the minimum is seven days.
- Approved with the default grace of thirty days, it gets `new_content_from = 2026-10-03T10:00:00Z` and `enforced_from = 2026-11-02T10:00:00Z`.

```text
 1.0.0  ────────●══════════════════════════════════════╗
               09-03                                    ║ contract
 2.0.0                       ○ · · ●═══════════════════╬══════════►
                           10-01  10-03   grace       11-02
                         published  new content      enforced
```

---

## What the Client Decides

Rule `contract-request` is in `enforce` mode; the lease margin is ten seconds.

| Instant | m1 `odrl:use` | m2 `ex:access` | m3 `odrl:read` | Why |
|:---|:---:|:---:|:---:|:---|
| 10-02 12:00 | ok | ok | **violation** | Only `1.0.0` is in force. |
| 10-03 09:59:55 | ok | **warning** | ok | `2.0.0` enters force a lease margin early. |
| 10-10 12:00 | ok | **warning** | ok | Grace window: both versions accepted. |
| 11-02 10:00:05 | ok | **warning** | ok | Still within the lease margin after `enforced_from`. |
| 11-05 12:00 | ok | **violation** | ok | Only `2.0.0` is in force. |

This is *expand, migrate, contract* (`REQ-SYS-007`): the new content is accepted first, the old content keeps working with a notice, and rejection starts only after `enforced_from` plus the lease margin.

A warning is forwarded with a notice that tells the sender exactly what is happening:

```http
VHub-Verdict: warning;gate=policy_intake;code="VERDICT_NOT_IN_HEAD";version="1.0.0";sunset=@1793613600
```

`version` is the older version that accepted the message and `sunset` the instant it stops being accepted.

---

## Agreements Outlive Their Version

On 10-10 an agreement **A1** carrying `ex:access` passes with a warning and is captured, bound to `1.0.0`.

| Instant | Event | Transfer under A1 |
|:---|:---|:---:|
| 11-05 12:00 | `1.0.0` is retired, but its package is retained because A1 references it. | admitted |
| 11-10 00:00 | A steward revokes `1.0.0`; `revoked_from` is 11-12 00:00 (request plus propagation window). The client emits `AGREEMENT_REVOCATION_SCHEDULED` for A1. | admitted |
| 11-12 00:00:05 | Revocation in effect, within the lease margin. | admitted |
| 11-12 00:00:10 | Lease margin over. | **rejected**, `AGREEMENT_VERSION_REVOKED` |

Retirement does not break existing agreements; only revocation does, and it is announced in advance.

## Reproducing It by Hand

Every process accepts a file clock, so the timeline can be replayed in seconds:

```bash
echo 2026-09-01T09:00:00Z > /tmp/clock
./bin/fake-idp serve --clock-file /tmp/clock
./bin/alexandria-server -config config/server.yaml -clock-file /tmp/clock
./bin/alexandria-client -config config/client.yaml -clock-file /tmp/clock
./bin/fake-idp token --sub sergio --clock-file /tmp/clock
```

Write a new instant to the file to move time forward. Tokens must be minted with the same clock, and the client must synchronize before each step for the listing to be current.
