# 4. Breaking Changes and Scenario F6

Sooner or later, every dataspace evolves. Suppose GreenCity decides that sharing raw fleet telemetry (`mob:shareTelemetry` from `1.0.0`) should be retired in favor of standard read-only access **`odrl:read`**.

Breaking every running partner integration at midnight would be chaos. Instead, Alexandria implements **expand, migrate, contract** (`REQ-SYS-007`), verified across the timeline in normative **Scenario F6** (replayed automatically by `make demo` and `TestE2E_F6`).

## GreenCity's Two Releases (`1.0.0` vs `2.0.0`)

Remember `N4` from [Tutorial 1](./01-first-profile-dsl): you can't retire an active term in one jump—so our `2.0.0` bundle includes an intermediate `1.1.0` `OdrlProfile` marking `shareTelemetry` as `deprecated` (`replaced_by: odrl:read`), plus the `2.0.0` `OdrlProfile` marking it `retired`, bound to `SpaceProfile` `2.0.0`:

| Release | Class | Accepted Policy Actions |
|:---|:---|:---|
| **`1.0.0`** | `initial` | `odrl:use`, `mob:shareTelemetry` |
| **`2.0.0`** | `breaking` | `odrl:use`, `odrl:read` |

---

## Timeline & Lifecycle Dates

- **September 1, 10:00 (`1.0.0` `initial`)**: Published and enforced immediately (`P = 2026-09-01T10:00:00Z`).
- **October 1, 10:00 (`2.0.0` `breaking`)**:
  - Attempting approval with `grace_window: P3D` is rejected (`422 DATES_GRACE_TOO_SHORT`—minimum is 7 days).
  - Approving with the 30-day default sets `new_content_from = 2026-10-03T10:00:00Z` (after the 2-day propagation window) and `enforced_from = 2026-11-02T10:00:00Z`.

```text
 1.0.0  ────────●══════════════════════════════════════╗
               09-01                                    ║ contract
 2.0.0                       ○ · · ●═══════════════════╬══════════►
                           10-01  10-03   30d grace    11-02
                         published  new content      enforced
```

---

## What `alexandria-client` Decides Along the Window

Assuming `contract-request` is in `enforce` mode (with a 10-second lease margin):

| Simulated Date | `odrl:use` | `mob:shareTelemetry` (old) | `odrl:read` (new) | Sidecar State & Explanation |
|:---|:---:|:---:|:---:|:---|
| **Oct 02, 12:00** | `forward` | `forward` | **`reject`** | `Active` (`1.0.0` only—`2.0.0` is `Scheduled`). |
| **Oct 03, 09:59:55** | `forward` | **`forward-notice`** | `forward` | `Transition` starts one lease margin before `new_content_from`. |
| **Oct 10, 12:00** | `forward` | **`forward-notice`** | `forward` | `Transition` grace window: both `1.0.0` and `2.0.0` work. |
| **Nov 02, 10:00:05** | `forward` | **`forward-notice`** | `forward` | Still inside the post-cutoff lease margin. |
| **Nov 05, 12:00** | `forward` | **`reject`** (`VERDICT_VIOLATION`) | `forward` | `Active` (`2.0.0` head only—`1.0.0` retired). |

Whenever a request relies on the older `1.0.0` during the grace window, the sidecar still forwards it cleanly to the connector **and attaches a `VHub-Verdict` warning header** so callers know when migration is due:

```http
VHub-Verdict: warning;gate=policy_intake;code="VERDICT_NOT_IN_HEAD";version="1.0.0";sunset=@1793613600
```

## Existing Agreements Outlive Retirement

What about an agreement **A1** negotiated on **October 10** under `mob:shareTelemetry`?
- **Nov 05 (Cutoff)**: Even though new contracts using `mob:shareTelemetry` are now rejected, **A1 keeps working** because it is bound to its captured `1.0.0` snapshot!
- **Nov 10 (Explicit Revocation)**: Only if `sergio` explicitly revokes `1.0.0` with a written justification does the client emit `AGREEMENT_REVOCATION_SCHEDULED`—and block transfers under A1 once `revoked_from` (request instant + propagation window + lease margin) arrives (`AGREEMENT_VERSION_REVOKED`).

## Replaying GreenCity `2.0.0` Yourself with a File Clock

<Steps>

### Start the lab with a file clock

Every Alexandria binary accepts `-clock-file` (`--clock-file` on `fake-idp`) so you can fast-forward months in milliseconds:

```bash
echo 2026-09-01T10:00:00Z > /tmp/clock
./bin/fake-idp serve --clock-file /tmp/clock
./bin/alexandria-server -config config/server.yaml -clock-file /tmp/clock
./bin/alexandria-client -config config/client.yaml -clock-file /tmp/clock
```

### Author `2.0.0` on Oct 1, then step through Oct 10 and Nov 5

Write `2026-10-01T10:00:00Z` to `/tmp/clock`, mint/refresh your steward identity, propose & approve the `2.0.0` YAML bundle (containing `OdrlProfile 1.1.0` deprecated + `OdrlProfile 2.0.0` retired + `SpaceProfile 2.0.0`), then write:
1. `2026-10-10T12:00:00Z > /tmp/clock` → press **`r`** (`Sync now`) → Status shows **`Transition`**; **Explain** accepts `mob:shareTelemetry` with `forward-notice`.
2. `2026-11-05T12:00:00Z > /tmp/clock` → press **`r`** (`Sync now`) → Status returns to **`Active`** (`2.0.0`); **Explain** rejects `mob:shareTelemetry` with `VERDICT_VIOLATION`.
