# 3. Validating DSP Traffic at the Edge

`alexandria-client` follows the `demo` namespace of [tutorial 2](./02-hub-governance-lifecycle) and proxies a connector — here the `fake-connector`.

```bash
ADMINAPI=http://127.0.0.1:9090
INGRESS=http://127.0.0.1:9080
```

<Steps>

### 1. Check synchronization

```bash
curl $ADMINAPI/status
```

Before the first release the state is `Onboarding`. Once the hub has published `1.0.0` and the client has synchronized, it becomes `Active`, with `last_accepted_listing.sequence` set, the hub DID resolved and `1.0.0` listed with role `scheduled` — it is known, but not yet in force.

```bash
curl $ADMINAPI/versions      # dates, reference state, package held or not
curl $ADMINAPI/readyz -i     # 200 once a listing has been accepted
```

### 2. Look at the rules

```bash
curl -i $ADMINAPI/rules
```

The seed holds 16 rules for the DSP messages. The `ETag` is the rule-set revision. The rule `contract-request` validates `POST /negotiations/{providerPid}/request` with the gates `dsp_message` and `policy_intake` in `enforce` mode.

### 3. Explain a decision

`:explain` answers what the proxy would do, without forwarding, recording or emitting anything:

```bash
curl -X POST "$ADMINAPI/rules:explain" -d '{
  "listener": "dsp-ingress",
  "method": "POST",
  "path": "/negotiations/urn:uuid:p-1/request",
  "body": {"@type": "ContractRequestMessage", "providerPid": "urn:uuid:p-1",
           "consumerPid": "urn:uuid:c-1", "action": "odrl:use"}
}'
```

While `1.0.0` is still scheduled, the answer is:

```json
{
  "rule": "contract-request",
  "state": "Active",
  "action": "reject",
  "code": "NO_VERSION_IN_FORCE",
  "vhub_verdict": "violation;gate=dsp_message;code=\"NO_VERSION_IN_FORCE\";…"
}
```

No version is in force yet, so a rule in `enforce` rejects. After `new_content_from` the same request gives `forward`; with `"action": "odrl:read"` it gives `reject` with `VERDICT_VIOLATION`, because the schema of `1.0.0` does not admit that action.

### 4. Send a message through the proxy

```bash
curl -i -X POST $INGRESS/negotiations/urn:uuid:p-1/request \
  -H "Content-Type: application/json" \
  -d '{"@type":"ContractRequestMessage","providerPid":"urn:uuid:p-1","consumerPid":"urn:uuid:c-1","action":"odrl:use"}'
```

- **Forwarded**: the connector's own response comes back, and `curl http://127.0.0.1:8282/_received` shows the body arrived byte for byte.
- **Rejected**: `400` with a DSP error body and the `VHub-Verdict` header; nothing reaches the connector.

### 5. Change a rule mode

Rule changes need the current revision in `If-Match`. Switch `contract-request` to `shadow`, which forwards everything but still reports:

```bash
curl -s $ADMINAPI/rules/contract-request | jq '.mode = "shadow"' > rule.json
curl -i -X PUT $ADMINAPI/rules/contract-request -H 'If-Match: "1"' --data-binary @rule.json
```

The response carries the new revision as `ETag`. Repeat step 4: the message is forwarded, and a `vhub.verdict` event is appended to the event sink.

```bash
tail -n 3 var/client/events.jsonl
```

### 6. Read the metrics

```bash
curl $ADMINAPI/metrics
```

`vhub_classifications_total` counts results per rule, gate, version and result.

</Steps>

<Callout type="info">
The three modes are a rollout path: `observe` to stay silent, `shadow` to measure what would be rejected, `enforce` to act. A rule can be moved between them at runtime; the change applies to the next message.
</Callout>
