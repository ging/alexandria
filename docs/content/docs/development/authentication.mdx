# Authentication & Authorization

Alexandria implements authentication and access control tailored to each deployment plane:
1. **`cmd/alexandria` (`internal/auth-proxy`):** Node-terminated OpenID Connect (OIDC) with PKCE against **Zitadel**, issuing encrypted `HttpOnly` session cookies and validating Bearer JWTs/opaque tokens ([ADR 0004](../adr/0004-authentication-terminated-at-the-node)).
2. **`cmd/alexandria-server` (`internal/server/adapters/auth_static` & `http_v1`):** Role-based Bearer authentication enforcing the §3.6 Governance Authorization Matrix (`REQ-HUB-017`, `DP-3`).

---

## 1. Node-Terminated OIDC in `alexandria` (`internal/auth-proxy`)

Rather than requiring browsers or CLI callers to orchestrate OAuth2 flows directly against Zitadel, authentication terminates at the Alexandria node:

1. **Initiate Login:** Navigating to `GET /api/v1/auth/login` generates an ephemeral state and PKCE verifier, sets a sealed state cookie, and redirects the user to Zitadel (`https://auth.127.0.0.1.nip.io:8443`).
2. **User Authenticates:** In local development, `task auth:bootstrap` seeds the default administrator (`admin@alexandria.auth.127.0.0.1.nip.io` / `Password1!`).
3. **Authorization Callback:** Zitadel redirects to `GET /api/v1/auth/callback?code=...&state=...`. Alexandria verifies the state, exchanges the code + PKCE verifier for tokens, and seals the session into an encrypted `HttpOnly`, `Secure`, `SameSite=Lax` cookie (`alexandria_session`).
4. **API Access & Introspection:** Subsequent `/api/v1/*` requests authenticate via the `alexandria_session` cookie or an `Authorization: Bearer <token>` header. JWTs are verified locally against Zitadel's cached JWKS (`jwks_refresh: 15m`), with optional fallback to OAuth2 token introspection (`auth_config.introspect: "fallback"`).

## 2. Role-Based Governance Auth in `alexandria-server` (`DP-3`, `REQ-HUB-017`)

In `alexandria-server`, all `/v1/*` management endpoints are protected by the `http_v1.Authenticator` port:

```go
type Authenticator interface {
    Authenticate(r *http.Request) (domain.Principal, bool)
}
```

### Static Token Adapter (`auth_static`)
By default (`DP-3`), `alexandria-server` loads `config/tokens.json`, which maps Bearer tokens to a `domain.Principal{Name, Roles}`:

```json
{
  "editor-token":   {"principal": "steward",     "roles": ["editor"]},
  "releaser-token": {"principal": "releaser",    "roles": ["releaser"]},
  "member-token":   {"principal": "alexandria-client", "roles": ["member"]}
}
```

- **Missing or Unknown Token:** Returns `401 Unauthorized` with `WWW-Authenticate: Bearer realm="vhub"` and an `application/problem+json` payload carrying `"code": "API_FORBIDDEN_ROLE"`.
- **Insufficient Role:** If an authenticated principal lacks the role required for an operation (e.g., an `editor` attempting `POST /v1/candidates/{id}:approve`), `alexandria-server` returns `403 Forbidden` with `"code": "API_FORBIDDEN_ROLE"` (`REQ-HUB-003`, `REQ-HUB-017`).

### Injecting Custom Auth into `alexandria-server`
When embedding `internal/server.Module` inside a larger composition root, pass any implementation of `http_v1.Authenticator` (such as an adapter backed by `internal/auth-proxy` or `internal/ssi-auth`) via `server.Deps{Auth: customAuth}`.
